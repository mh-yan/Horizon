## [PostgreSQL 19 Released with WAIT FOR LSN for Read-Your-Writes Consistency](https://simonwillison.net/2026/Nov/19/postgresql-19/) ⭐️ 9.0/10

PostgreSQL 19 was released on November 19, 2026, two months later than the usual September schedule, after the team dealt with a surge of AI-reported vulnerabilities. The headline feature is the new WAIT FOR LSN command, which lets a session on a standby server wait until the standby has replayed the write-ahead log (WAL) up to a specified log sequence number (LSN) before running a query, enabling read-your-writes consistency for applications that send reads to standbys. This feature solves a long-standing pain point for applications that scale reads by routing them to standby servers: without it, a user might write data on the primary and then fail to see that write on a standby due to replication lag. By providing a built-in, standardized mechanism for read-your-writes consistency, PostgreSQL 19 reduces the need for hand-rolled workarounds and makes it easier to build consistent, read-scalable applications on the world's most popular open-source database. The WAIT FOR LSN command accepts an optional TIMEOUT clause (e.g., WITH (TIMEOUT '0.1s')) that raises an error if the standby does not catch up within the specified time, and it also supports standby modes (standby_replay, standby_write, standby_flush) with a NO_THROW option to return a status string instead of throwing errors. The typical pattern involves capturing the current WAL insert LSN on the primary via pg_current_wal_insert_lsn(), storing it (e.g., in a signed cookie), and then issuing WAIT FOR LSN on the standby before reading.

rss · Simon Willison · Nov 19, 20:43

**Background**: PostgreSQL uses write-ahead logging (WAL), where every change is first written to a log before being applied to data files; each WAL record has a log sequence number (LSN), a 64-bit position in the WAL stream. In streaming replication, a standby server continuously replays WAL from the primary, but there is always some replication lag, meaning a standby may not immediately reflect the latest writes. Read-your-writes consistency is a guarantee that a user who performs a write will subsequently see that write when reading, and achieving it on standbys traditionally required custom application logic. The release delay was caused by a flood of vulnerabilities found by AI-assisted code review, which found defects faster than the team could fix them, leading to 8–10 features being reverted to PostgreSQL 20.

Apple has consistently refused to build backdoors into its products, arguing that doing so would weaken security for all users.
